One Save per account row, and the flash that never left

Tick a profile in "Accounts and roles", press Save, and nothing happened. The
ticks lived in one form and the button in another, and the button belonged to
the *role* form: it posted the role and the ticks never left the browser.
Nothing on the page said so -- the button worked and it even flashed a
confirmation, so the row read as saved.

A row is one thing to configure, so it is now one form posted to
/settings/users/save, which applies the role and the profile replacements
together. An unticked box is a revocation, so an empty tick list clears the
row rather than meaning "unchanged". Delete is not a second form nested inside
the row -- HTML forbids that -- it is a button carrying formaction.

/settings/users/role and /settings/users/grants are gone rather than left
dormant: each applied half of what the row claims to save, which is how the
split happened.

Two things the endpoint refuses to guess at. The role goes first, because it is
the half that can be refused (the last admin cannot be demoted) and a refused
save must not leave the profiles half written. And the role is only touched when
the form carries one: normalise_role(None) answers the least privileged role, so
a missing select would quietly demote everyone except the last admin -- the one
account set_role protects on its own.

Separately, this page showed flashes but never faded them. Three other pages
render the same banner and dismiss it after seven seconds; this one had the
markup and not the script, so a stale confirmation sat above the accounts until
a reload. A test now walks every template that calls get_flashed_messages and
requires the dismissal.
